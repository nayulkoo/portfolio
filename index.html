해결해야 했던 문제

  • 매뉴얼과 결재 문서처럼 구조가 다른 원천 데이터를 검색/RAG에 활용할 수 있는 공통 구조로 정리해야 했습니다.
  • 원본 파일과 메타데이터를 변경 이력 기준으로 증분 수집하고, 재처리 범위를 통제해야 했습니다.
  • 파싱·청킹·임베딩·색인 단계가 길어질수록 문서별 처리 상태와 산출물 위치를 추적할 수 있어야 했습니다.

  • RAG 시스템용 데이터 수집·처리 파이프라인 설계 및 개발

챗봇 솔루션의 시나리오 표현력과 AI 기능 고도화

정적 응답 중심의 챗봇 솔루션에 Groovy 기반 스크립팅, 기능 블록 기반 시나리오 편집, LLM 기반 Q&A 데이터 생성, RAG 기반 질의응답 기능을 더해 약 30여 개 고객사에 도입된 핵심 제품의 고도화에 기여했습니다.

해결해야 했던 문제

  • 정적 응답 중심 구조만으로는 고객별 대화 시나리오, 동적 콘텐츠 생성, RPA 흐름을 충분히 표현하기 어려웠습니다.
  • 운영자가 기능 블록, 조건, 외부 연계 로직을 조합해 복잡한 시나리오를 관리할 수 있어야 했습니다.

대표 경험 03 RAG 솔루션 성능 및 품질 고도화

RAG 응답 성능과 품질 개선을 위한 LLM 처리 구조 고도화

Ollama 기반 처리 구조에서 발생한 동시 요청 병목을 vLLM 전환으로 완화하고, 고객사 데이터 특성에 맞춰 프롬프트·모델·파라미터를 조정하며 RAGAS 기반 품질 평가 루프를 적용했습니다.

해결해야 했던 문제

  • Ollama 기반 LLM 처리 구조에서 동시 요청 처리 병목이 발생했습니다.
  • 고객사 데이터 특성과 요구사항에 따라 시스템 프롬프트, 모델, 파라미터를 반복적으로 조정해야 했습니다.
  • 답변 정확도와 응답 일관성을 감각이 아닌 평가 결과를 바탕으로 개선해야 했습니다.

담당한 역할

  • Ollama 기반 LLM 처리 구조를 vLLM 기반 구조로 전환
  • 시스템 프롬프트, 모델, 파라미터 튜닝
  • RAGAS 기반 품질 평가와 개선 반복

구조와 주요 결정

  • Ollama → vLLM 전환은 동시 요청 병목을 LLM 서빙 구조와 처리량의 문제로 판단하고, Continuous Batching과 효율적인 KV Cache 관리를 지원하는 vLLM 기반 구조로 개선한 결정이었습니다.
  • RAGAS 기반 평가 루프는 응답 속도 개선만으로는 RAG 답변의 정확도와 일관성을 보장하기 어렵다고 판단해, 평가 결과를 기반으로 프롬프트·모델·파라미터 튜닝 방향을 결정하기 위해 적용했습니다.
  • OpenSearch + BGE-M3/Reranker 구성은 답변 품질을 LLM 성능만의 문제가 아니라 검색·리랭킹·생성 과정 전체의 문제로 판단하고, 각 단계의 품질을 함께 개선하기 위해 적용한 구조였습니다.
고려한 점
vLLM 전환은 처리량 개선에 유리했지만 구조 복잡도와 운영 고려사항이 늘 수 있었습니다.
또한 리랭킹과 평가 루프는 답변 품질 향상에 도움이 되었지만 응답 지연과 운영 비용이 증가할 수 있어 품질과 성능의 균형을 함께 고려했습니다.
결과
Ollama 기반 동시 요청 병목을 vLLM 전환으로 완화해 테스트 환경 기준 처리 성능을 기존 대비 10배 이상 개선했습니다.
또한 RAGAS 기반 평가와 튜닝을 적용해 성능 개선과 답변 품질 향상을 반복적으로 검증할 수 있는 개선 체계를 구축했습니다.
